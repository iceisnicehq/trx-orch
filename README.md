# TRX Orchestrator — личная предыстория FIFO и учёт исходных долей (release 26)

React/Vite/Tailwind/Cytoscape, Node.js/TypeScript/Express/TronWeb, Prisma/SQLite с WAL, Docker Compose. По умолчанию — **TRON Mainnet, реальные переводы, ручное одобрение**. Всегда 17 слотов в конфигурации; участников кампании — **от 2 до 17**.

**Rebalance, досрочный возврат, возврат по расписанию и защита дедлайна возвращают каждому его исходный 1 TRX и ставят игру в паузу. Они не создают выплат учителю. Только End Game с паролем разрешает выплаты и переход в COMPLETE.**

## 1. Обновление существующей установки

**Release 26 исправляет предысторию: вместо всей связанной группы показывает только прежние переводы с долей выбранного участника.** Во вкладке «Мой 1 TRX · полный план» остаются два независимых переключателя: **Моя предыстория в схеме и таблице** и **Добавить мою предысторию в CSV**. Оба изначально выключены; прежний выбор браузера сохраняется. Они меняют только отчёт, не план или одобрения.

Для RANDOM/LIST применяется явное правило **FIFO**: исходная игровая ставка участника — 1 000 000 Sun; на адресе сначала расходуются наиболее ранние поступления. Перевод может содержать доли нескольких владельцев. Расчёт включает в личный отчёт только строки, в которых `owner_amount_sun > 0`, даже если этот перевод идёт между двумя другими адресами. Не относящиеся к вашей доле операции исчезают из схемы и CSV. Точность — до одного Sun; личный резерв не участвует.

**FIFO — восстановленный расчётный учёт, не единственный доказуемый путь конкретных Sun.** В [TransferContract TRON](https://developers.tron.network/docs/tron-contracttype) есть отправитель, получатель и сумма, но нет исходного владельца каждой части. Повторные RPC-запросы не восстановят отсутствующие теги принадлежности. RANDOM/LIST такие теги не записывали; поэтому старый отчёт явно помечает FIFO. Сохранённые доли SMART имеют отметку RECORDED и используются напрямую.

REBALANCE входит в маршрут как обычный подтверждённый перевод. Он **не сбрасывает FIFO**: выравнивание физических балансов не доказывает возвращение определённых Sun. Начало каждой SMART-кампании — отдельная видимая граница нового учёта ставки, не дополнительная on-chain транзакция. При недостаточных или противоречивых старых данных сохраняется корректный префикс и показывается «Предыстория частичная»; недостающие средства не выдумываются. На текущую игру это не влияет.

Расчёт кешируется между отчётами разных участников. Новые подтверждённые/изменённые записи обновляют кеш. После перезапуска он воспроизводится из сохранённого журнала; новый RPC-запрос при каждом обновлении сайта не нужен.

**Новых миграций в release 26 нет.** Все десять прежних миграций сохранены. API только читает историю: исполняемый план, очередь, Auto, одобрения, ускоренное расписание и учёт текущих долей остаются прежними. Пересоберите **API и web** по командам ниже, обновите страницу через Ctrl+Shift+R. Новый Start или Rebalance не требуется.

**Release 24 добавляет защищённую кнопку «Ускорить по Bandwidth» для уже запущенного полного плана.** Она пересчитывает время оставшихся MIX-переводов по восстановлению ресурсов, сохраняя маршруты, суммы, последовательность, состав долей и одобрения. Исходное `plannedAt`, подтверждённая история, txID и уже подписанные транзакции остаются прежними. После каждого нового подтверждения будущий прогноз обновляется по фактическому расходу. Возвраты сохраняют свою карту и суточные интервалы отправителей; их начало переносится вслед за ускоренным MIX.

Ускорение **не включается автоматически при обновлении**. После установки этого обновления обновите страницу через Ctrl+Shift+R, затем в разделе «РАСПИСАНИЕ MIX» нажмите **Ускорить по Bandwidth** и введите пароль. Новый Start, Rebalance или перегенерация текущего плана не нужны. Если транзакция уже отправлена, движок сначала проверяет её сохранённый txID, затем пересчитывает оставшееся время.

После включения следующий MIX требует **минимум 407 бесплатных Bandwidth**, сохранённого одобрения и подтверждения предыдущего шага. Дополнительный час ожидания и ограничение в 24 часа между MIX снимаются. Затем действует случайная пауза: **1–2 минуты при полной квоте, 5–10 минут при частичной**. Поздний кошелёк не обгоняет предыдущий: если Ann стоит перед TAG, TAG ждёт подтверждения Ann. Одобренные переводы могут отправиться раньше прежних дат; вся кампания может завершиться раньше исходных 36 дней. Номер дня плана в этом режиме обозначает раунд алгоритма, а не календарные сутки. Ускорение и выбранные паузы сохраняются после выключения сервера.

**Rebalance и полный возврат заканчиваются паузой. Учителю переводит только End Game.** Ускорение не включает Auto, не добавляет одобрения и не продлевает дедлайн. Перегенерация, выбор другого плана и обмен по-прежнему запрещены после начала подписания.

Release 24 включает прежние исправления: очередь записей SQLite против P1008/P2028, независимую загрузку разделов сайта, читаемое оформление кнопок и сохранение альтернативных вариантов. Планы, ручные одобрения, Auto, позиции долей, личный резерв, Telegram и текущая фаза сохраняются.

**Сохраните свои `.env`, `config/wallets.json`, имя проекта Compose и volume базы. Не заменяйте реальные кошельки пустым шаблоном из архива.** При обновлении с версий до release 24 применяется десятая миграция `20261004020000_adaptive_timing`: только новые поля режима/ожидания ресурса. Все девять прежних миграций сохранены без изменений. Кампания из версий до release 24 получает режим `DAILY` до включения ускорения. Уже сохранённый `BANDWIDTH` из release 24 остаётся включённым. Для этого обновления нужно пересобрать **и API, и web**.

Сначала сделайте резервную копию, остановив API:

Положите `trx-orchestrator-release26.zip` рядом с каталогом `trx-orchestrator`. После успешной копии базы выполните простой перенос через staging:

Свои `.env` и `config/wallets.json` не копируйте из staging. Миграции применяются автоматически. Используйте отдельный каталог `upgrade-staging26`, чтобы файлы предыдущего обновления не попали в эту версию. При уже включённом Auto сохранённая игра может продолжить прежние одобренные переводы сразу после запуска API.

Для старых версий до полного плана: RANDOM/LIST переходит в **LEGACY_PAUSED**. Неотправленные MIX и их одобрения отменяются; подписанная/отправленная транзакция проверяется по сохранённому txID. Если кошельки ещё не сбалансированы, выполните **Rebalance старой игры**, одобрите возвраты и дождитесь паузы. Затем выберите участников, сгенерируйте и выберите вариант, нажмите **Start**. Уже начатый старый End продолжает сохранённые выплаты.

Полный план release 20–23 сохраняется. Если он ещё не начал подписываться, **Вернуться к настройке** сохранит его как альтернативу и переведёт систему в PREPARING с отменой прежних одобрений. После начала исполнения план продолжается. Изменить его схему можно только после возврата исходных долей и подготовки новой кампании; ускорение меняет лишь время исполнения существующей схемы.

Галочки Auto сохраняются. Для ручного наблюдения выключите Auto до нового Start. Не используйте `down -v`, `migrate reset` или удаление БД. Старый образ нельзя запускать поверх обновлённой базы; восстановление старой копии после новых on-chain переводов требует сверки с сетью.

## 2. Mainnet, API key, SafePal и JSON

1. Войдите/зарегистрируйтесь на [TronGrid](https://www.trongrid.io/), откройте **API Keys**, создайте ключ и вставьте в `TRON_PRO_API_KEY`. Это доступ к RPC и его квотам, **не приватный ключ кошелька**. [Официальная инструкция](https://developers.tron.network/reference/select-network).
2. Для новой установки: `cp .env.example .env`. Оставьте `TRON_MODE=live`, `TRON_FULL_HOST=https://api.trongrid.io`, `WEB_BIND_HOST=127.0.0.1`. Nile (`api.nileex.io`) — тестовая сеть, не Mainnet.
3. Задайте собственный `ADMIN_PASSWORD`. При пустом значении используется исходный `P@ssw0rd12344321`. Пароль требуется для Start, End, возврата, смены учителя, Approve и переключателей кошельков.
4. Заполните **все 17 слотов** `config/wallets.json`: `slot` по порядку 1–17, уникальный адрес, соответствующий приватный ключ — 64 hex-символа. Нулевой баланс у выключенного слота допустим. Для включения Mix нужны активация и не менее 1 TRX.
5. Укажите полный проверенный адрес учителя. Сервер проверяет checksum/активацию, но не определяет владельца адреса. Приватный ключ учителя не нужен; учитель не может быть участником.

Сокращённый пример структуры — готовый шаблон содержит 17 слотов:

```json
{
  "teacherAddress": "ПОЛНЫЙ_АДРЕС_TRON",
  "wallets": [
    {"slot": 1, "address": "ПОЛНЫЙ_АДРЕС_1", "privateKey": "64_HEX_СИМВОЛА"},
    {"slot": 2, "address": "ПОЛНЫЙ_АДРЕС_2", "privateKey": "64_HEX_СИМВОЛА"}
  ]
}
```

Это **серверное подписание**: Approve разрешает серверу подписать перевод; подтверждения в SafePal не появятся. Для аппаратного SafePal с неэкспортируемым ключом такой способ не подходит. Seed-фразу в JSON вставлять нельзя. Ключи, конфигурация и резервные копии должны быть доступны только администратору; ключи не передаются в SPA, отчёты или Telegram.

Для стандартного TronGrid Mainnet ключ обязателен; для доверенного альтернативного full node это зависит от провайдера. Квота RPC не является комиссией TRX.

`TRON_MODE=mock` — отдельный симулятор с демонстрационными адресами и локальными балансами, без настоящих переводов. Для ручного Approve в Mainnet он не нужен. **Не переключайте сеть, live/mock или набор адресов на одной базе.**

## 3. Docker и SSH

Нужны Docker Engine и современный Compose CLI-плагин. Используйте **`docker compose` с пробелом**, не старый Python `docker-compose` с ошибкой `http+docker`. Если Ubuntu 22.04 не находит `docker-compose-plugin`, подключите официальный репозиторий Docker по [инструкции Ubuntu](https://docs.docker.com/engine/install/ubuntu/), затем установите плагин.

После заполнения файлов из каталога проекта:

```bash
docker compose version
docker compose up -d --build
docker compose logs -f api web
```

База и миграции инициализируются автоматически. Web по умолчанию слушает `127.0.0.1:8080` сервера, API не публикует отдельный порт. На своём компьютере:

```bash
ssh -L 8080:127.0.0.1:8080 root@IP_СЕРВЕРА
```

Откройте `http://localhost:8080`. `WEB_PORT` меняет порт, `WEB_BIND_HOST` — привязку. Для публичного размещения нужен HTTPS перед Nginx. Образы устанавливают OpenSSL для Prisma; web проверяет наличие собранного `index.html`.

## 4. Полный план и одобрения

1. Отметьте **Mix** у минимум двух готовых кошельков, подтвердите паролем. Оставьте Auto выключенным.
2. В разделе **Варианты полного плана** нажмите **Создать вариант плана**. По умолчанию: **36 дней — 28 раундов MIX и до 8 дней возврата; дедлайн через 42 дня**. Допустимо 18–60 дней. Сервер требует минимум четыре дня запаса до дедлайна после расчётного завершения возврата.
3. **Создать новый вариант** создаёт и выбирает новую альтернативу для подготовки, сохраняя предыдущие. Пустое поле дедлайна сохраняет **точное существующее значение** (в том числе ваш дедлайн в 41 день), а не продлевает его. Длительность можно уменьшить явно. Если времени не хватает, генерация/выбор/Start отклоняются без отправок.
4. В списке **Вариант для просмотра** сравнивайте диапазоны и таблицу по игрокам. Просмотр не меняет выбор для Start. **Схема / CSV** открывает полное движение ставки в этом варианте. **Использовать этот вариант** с паролем выбирает вариант и восстанавливает его состав участников. У уже выбранного варианта кнопка показывает **Этот вариант выбран** и недоступна. Можно уйти на любой сохранённый допустимый вариант.
5. Выберите двух разных игроков и нажмите **Поменять планы игроков местами** с паролем. Сохраняется новый производный вариант. Переставляются адреса в маршрутах, владельцы долей и профили во всём плане; приватные ключи, старые отчёты и история остаются. Исходный вариант не перезаписывается. Пока два разных игрока не выбраны, кнопка обмена недоступна.
6. В **PREPARING** ничего не подписывается и не отправляется, даже при включённом Auto. DRAFT в очереди — предпросмотр, не одобрение. Варианты и выбор переживают выключение сервера. Изменение галочек Mix снимает выбор, но не удаляет варианты; сгенерируйте или выберите подходящий вариант снова.
7. Нажмите **Start · выбранный план** с паролем. Сервер заново проверит баланс, резерв, активацию и дедлайн. День 1 отсчитывается от этого запуска; исходные даты генерации в DRAFT являются ориентиром. Дедлайн не меняется. Маршруты и состав вкладов выбранного варианта копируются без перегенерации.
8. Очередь показывает **один ближайший открытый шаг на отправителя**. Approve можно дать заранее: он переживает перезапуск и не обходит расписание, зависимости или Bandwidth. Одобрения предыдущего исполнения не копируются в новый Start.
9. Для ускорения уже запущенной кампании нажмите **Ускорить по Bandwidth** с паролем. Схема и одобрения сохранятся, изменятся текущие даты. Движок ждёт первый MIX по порядку; номер дня становится номером раунда.
10. Позже включите **Auto** по отдельности у нужных отправителей. Оно одобряет существующие и будущие исходящие MIX/возвраты, а после End — выплаты. Выключение снимает только неотправленные автоматические одобрения; ручные остаются. Подписанную/отправленную транзакцию галочка не отменяет.

**Генерация, выбор другого варианта и обмен доступны только до первого подписания в текущей кампании.** Блокировка сохраняется в БД даже при ошибке подписания/отмене broadcast из-за ресурса и при перезапуске. Сервер возвращает 409 на устаревшие команды из открытой вкладки. Для новой подготовки после исполнения нужно сначала вернуть исходные доли и дождаться паузы; это новая кампания, а прежняя история сохраняется.

Состав кампании фиксирован до восстановления исходных долей. Для добавления кошельков сначала Rebalance/возврат → пауза → изменение Mix → новый полный план. Старые кампании доступны в архиве. Ранее вступивший кошелёк остаётся учтённым для окончательной выплаты, даже если не участвует в следующей кампании.

RANDOM/LIST убраны из интерфейса. Старые записи и код восстановления сохранены для совместимости. Replan не переписывает действующую кампанию. «Ускорить по Bandwidth» изменяет только текущее время существующих шагов, не выбранный шаблон.

## 5. Дробление, объединение и бюджет операций

Новый генератор выравнивает **истории исходного 1 TRX**, а не только число отправок адреса. Для каждого владельца шаги должны попасть в интервал `floor(среднее) − max(2, ceil(0.10 × среднее))` … `ceil(среднее) + max(2, ceil(0.10 × среднее))`; для разветвлений используется 0.20 вместо 0.10. Требуются разные взвешенные структуры схем. Генератор пробует до 128 seed; неподходящий план не сохраняется и не исполняется. Прежний сохранённый вариант может выходить за новые пределы: он явно помечен, но остаётся доступным.

Шаг ставки — реальный перевод, содержащий её долю, включая отправки другими адресами и возврат. Один такой шаг может одновременно принадлежать историям нескольких игроков. Поэтому 90 шагов на ставку не означают 90 отправок с её исходного адреса. В стандартном плане каждый адрес делает 28 MIX-отправок; возвраты считаются отдельно и могут отличаться. Счётчик ветвей считает частичный уход с сохранением остатка; объединения показаны отдельно.

Каждая ставка — **1 000 000 Sun**, расчёты целочисленные. Seed, профили, все маршруты, исходные даты, зависимости и доли в каждом переводе записываются **атомарно до отправок**. Симуляция проверяет отсутствие перерасхода и сохранение каждой ставки до её возврата.

Профили и дни дробления выбираются случайно, с разными окнами:

| Профиль | Минимальные доли |
|---|---|
| QUARTERS | С выбранного дня — 0,25 TRX; без 0,125 |
| LATE_QUARTERS | Сначала 0,5, ближе к концу — 0,25 |
| EIGHTHS | В разные дни — 0,5, затем 0,25, затем 0,125 |

Это минимальный размер доли, а не обязательная сумма каждого перевода. Несколько долей владельца могут идти вместе. Например, нативный перевод 0,75 TRX содержит `A: 0,25 + B: 0,375 + C: 0,125`; для B доля 0,375 возможна после допуска 0,125. Такое объединение требует **одной транзакции**, а не по одной на вклад.

Каждый раунд меняет один или несколько циклов по участникам, выбирает нативные пакеты 0,5/0,75/1 TRX и перемежает шаги разных циклов. Выбор отдаёт приоритет ставкам с меньшим числом шагов, разветвлений и объединений и новым направлениям; несколько владельцев объединяются в один пакет. Каждый физический кошелёк делает **одну исходящую MIX за раунд**. В конце раунда на каждом адресе снова 1 TRX игровых средств, но в них уже могут быть доли разных участников. Между шагами баланс может быть 1,25 или 1,75 TRX. Генератор требует разных взвешенных структур отчётов, а не только разных подписей узлов.

Для 17 участников стандартный план: **476 MIX** (`17 × 28`) плюс до **136 прямых возвратов** (`17 × 8`). MIX-отправок с каждого адреса поровну; число возвратов и шагов конкретной исходной ставки отличается. Восемь суток возврата — бюджет по отправителям после полного раунда. Досрочный останов внутри раунда может потребовать большего бюджета; он рассчитывается по фактическому составу. Выплаты добавляются только по End Game — по одной с каждого вступившего адреса.

TRX взаимозаменяемы: сеть не помечает Sun владельцем. Принадлежность — проверяемый внутренний учёт приложения по сохранённому составу переводов. Публичные отчёты раскрывают этот учёт; гарантии анонимности нет.

## 6. История, схема, CSV и состав баланса

Нажмите узел графа или кошелёк в списке:

- **Мой 1 TRX · полный план** показывает движение исходной ставки, включая переводы между чужими адресами, текущие подтверждённые места хранения, все будущие шаги и архив кампаний.
- **История адреса** показывает физические входящие/исходящие этого адреса, фильтры статусов и загрузку старых записей.

**Моя предыстория в схеме и таблице** добавляет старые подтверждённые операции с этой долей перед выбранным планом. **Добавить мою предысторию в CSV** управляет только скачиваемым файлом: можно включить предысторию в CSV независимо от схемы. Операции с нулевой долей этого участника исключены в обоих случаях. Старая общая история группы из release 25 больше не добавляется.

Янтарные прямоугольники показывают остаток **вашей ставки** на адресе; шестиугольники — реальные прошлые переводы с **вашей долей и всей нативной суммой отдельно**. FIFO помечает расчётную предысторию, RECORDED — сохранённые доли прежних SMART-кампаний. На стрелках сумма означает долю этой ставки. Серые сплошные линии сохраняют остаток; серый пунктир обозначает новый период учёта и не является переводом.

Пример FIFO: B уже держал свою исходную 1 TRX, затем получил 0,5 TRX от A. Если B отправляет 1,25 TRX в C, этот перевод содержит 1 TRX B и 0,25 TRX A; ещё 0,25 TRX A остаются на B. В отчёте A шаг B → C показывает долю 0,25 при полной сумме 1,25. Если B отправляет только 1 TRX, в FIFO это исходные средства B: шаг не входит в историю ставки A. Это объяснимое правило учёта, а не установленная сетью принадлежность монет.

В CSV с личной предысторией:

- `report_section`: PREHISTORY или CAMPAIGN;
- `attribution_basis`: RECONSTRUCTED для старого расчёта, RECORDED для сохранённых SMART-долей;
- `attribution_method`: FIFO или RECORDED; `history_period_id` отделяет периоды нового учёта;
- `owner_amount_sun` / `owner_amount_trx`: только положительная доля выбранного владельца; `native_amount_sun` / `native_amount_trx`: вся сумма транзакции;
- `packet_ownership`, `from_wallet_ownership_after`, `to_wallet_ownership_after`: состав пакета/игровых балансов по соответствующему правилу. Для FIFO это восстановленный расчёт, резерв Sun исключён;
- `history_initial_stake_sun`: исходное допущение 1 000 000 Sun. `history_complete=true` означает, что воспроизведение сохранённых CONFIRMED не встретило противоречия; это не гарантия полноты всей on-chain истории;
- `transfer_mode`: RANDOM/LIST/REBALANCE/SMART/RETURN/PAYOUT; LEGACY означает, что точный режим не сохранился в аудите. Режим не угадывается по сумме;
- `source_campaign_id`: ID прежней кампании, если он есть;
- `confirmed_utc`: сохранённое время блока; `recorded_confirmation_utc`: время записи подтверждения. `execution_msk` и `execution_time_basis` отличают BLOCK от RECORD;
- будущие даты и фактические даты разделены: `scheduled_utc` / `scheduled_msk` остаются сохранённым окном расписания.

Полные адреса, txID и известный фактический Bandwidth сохраняются. Неизвестный Bandwidth остаётся пустым. Счётчики сложности выбранного SMART-плана и его текущие позиции не изменяются от переключателей. Неодобренные, отменённые, не подтверждённые и более поздние записи не добавляются. Архив кампании получает историю только до своего начала; предпросмотр будущего варианта — до текущего конца журнала.

SVG включает только вашу подключённую предысторию, положительные доли и легенду полных адресов. Для всех участников используется одно и то же правило FIFO: один Sun не может одновременно быть приписан двум людям. Расчёт не изменяет таблицы Allocation/OwnershipBalance. Кеш ограничен восемью историческими снимками и пятью минутами; проверка версии журнала обновляет его при изменении CONFIRMED. Ошибка чтения не кешируется. После перезапуска результат восстанавливается из базы.

Отчёт использует сохранённые записи приложения. Внешние операции SafePal и удалённая история автоматически не импортируются. Если этих операций не хватает для допустимого расчёта, период помечается частичным, без фиктивных поступлений. API TRON может предоставить/проверить дополнительные факты о переводах, но не выбрать их первоначального владельца вместо правила атрибуции.

Стрелки схемы направлены **от прошлого к будущему**. Прямоугольник — остаток доли, шестиугольник — реальный перевод; серые линии сохраняют остаток, бирюзовые шаги подтверждены, зелёные пунктирные запланированы. Можно двигать/масштабировать схему, ограничивать днём и скачать **SVG** с легендой полных адресов. Обновление статусов не сбрасывает расположение узлов.

**Экспорт полного CSV**: день/номер/тип/статус, полные адреса, доля владельца и вся сумма перевода в Sun/TRX, состав пакета, общий игровой баланс и состав двух адресов после шага, исходное время UTC, текущее окно UTC/MSK, время подтверждения, txID и фактический Bandwidth **всего перевода**. В колонке `timing_mode` указан DAILY/BANDWIDTH; исходный день и время отделены от актуального прогноза и подтверждения. Расход по долям не выдумывается. CSV UTF-8 с BOM; в Excel при импорте выберите разделитель «запятая».

Состав после будущего шага — прогноз полного плана; текущие места хранения основаны только на подтверждениях. Кошельки показывают on-chain баланс, личный резерв и подтверждённые доли, например `Node 3: 0,25 + Node 7: 1,00`. «1 tx» на графе — количество транзакций; сумма TRX показана отдельно. Отменённые будущие шаги сохранены в истории/БД, но исключены из актуального CSV и схемы.

Для учителя состав в отчёте учитывает только выплаты этой кампании, а не его полный on-chain баланс.

## 7. Bandwidth и расписание

Только нативные **TransferContract**, без смарт-контрактов/Energy. Получатель должен быть активирован, чтобы не возникла плата создания аккаунта.

В активной кампании кнопка **Ускорить по Bandwidth** с паролем переключает расписание с `DAILY` на `BANDWIDTH`. Она доступна в фазе CAMPAIGN, в том числе после начала исполнения. Закрытие, пауза и HALTED её не допускают. Повторный запрос не создаёт новый план и не дублирует переводы.

| Проверка | Суточный режим DAILY | Ускоренный MIX BANDWIDTH |
|---|---|---|
| Бесплатный ресурс перед построением и broadcast | `max(400, оценка размера)` | `max(407, оценка размера)` |
| Минимум 24 часа от исходящей отправки этого адреса | Да для MIX/RETURN | Нет для MIX; сохраняется для RETURN |
| Часовой запас в прогнозе восстановления | Да при нехватке ресурса | Нет для MIX |
| Последовательность MIX | По номеру шага | Тот же порядок, без обгона |
| Одобрения | Approve или Auto отправителя | Те же сохранённые одобрения |
| После возвращения долей | Пауза | Пауза |

Перед построением вызывается `tronWeb.trx.getBandwidth` и проверяется именно **бесплатная квота** через `getAccountResources`, а не сумма бесплатного и стейкнутого ресурса. После подписания учитывается оценка размера; перед broadcast бесплатный ресурс проверяется повторно. Порог 407 не заменяет проверку размера: если требуется больше, движок запоминает более высокий порог и ждёт его. Ручной Approve не разрешает перевод с недостаточным ресурсом.

В ускоренном режиме порядок такой:

1. Берётся первый оставшийся MIX по `sequence`. Он должен быть одобрен, а его предшественник подтверждён. Готовые более поздние отправители ждут.
2. Прогноз использует свежий остаток, время и стоимость подтверждённых отправок. Календарное окно следующего дня не задерживает готовый MIX.
3. При нехватке ресурса следующий живой запрос назначается не дальше чем через **5 минут**, либо раньше, если расчётный порог близко. Проверяется отправитель первого шага; снимки остальных нужны только для прогноза и обновляются после подтверждений/перезапуска. Обычный опрос сайта имеет собственный кеш. Неопределённый ответ RPC не разрешает отправку.
4. Когда свежая проверка показывает нужный ресурс, сохраняется время готовности и случайная пауза: **1–2 минуты при полной бесплатной квоте** (обычно 600 из 600), иначе **5–10 минут**. Перед отправкой проверка повторяется. Если ресурс уменьшился, пауза отменяется и снова начинается ожидание ресурса.
5. Подтверждённая квитанция даёт фактический расход. Будущие MIX-даты пересчитываются в прежней последовательности, с учётом прогнозируемых расходов предыдущих шагов. Карта возвратов остаётся прежней, её начало сдвигается вслед за новым окончанием MIX.

Пример одного расхода: 600 − 267 = 333. Простейший прогноз до 407: `(407 − 333) / (267 / 24)` ≈ **6 часов 39 минут**, затем случайная пауза 5–10 минут. Для расхода 260 или 300 прогноз другой. Нельзя считать восстановление постоянными `600 / 24`; повторные расходы и внешняя активность меняют оценку. Будущие расходы ещё неизвестны, поэтому используется последняя подтверждённая стоимость, а до первого расхода — консервативная оценка 400. Это **прогноз времени**, не разрешение отправки и не обещание двух переводов ежедневно. [Ресурсная модель TRON](https://developers.tron.network/docs/bandwidth-and-energy).

Выбранные паузы, время готовности, следующий запрос и повышенный порог записываются в БД. Перезапуск не выбирает новую паузу и не подписывает замену транзакции в полёте. Помимо минутного фонового тика используются отдельные таймеры для сохранённых пауз: время не округляется постоянно до ровных двух минут. Нерегулярные интервалы не гарантируют сокрытие автоматизации в публичной сети.

Оригинальное `plannedAt` сохраняется. `scheduledAt` показывает актуальный прогноз в очереди, Telegram, отчёте и CSV; действительная дата подтверждения сохраняется отдельно. В ускоренном режиме «день» исходного плана — **раунд алгоритма**, который может выполниться раньше календарных суток. Вся кампания может закончиться раньше исходной даты; дедлайн остаётся неизменным. Полный возврат и досрочный Rebalance сохраняют консервативные суточные интервалы отправителей и заканчиваются паузой. Выплаты добавляет только End Game.

Сеть не даёт атомарно зарезервировать бесплатный ресурс между проверкой и блоком: абсолютную гарантию отсутствия комиссии приложение дать не может. Оно отказывается отправлять при нехватке данных/ресурса, проверяет квитанцию и останавливается при обнаруженной комиссии/недостаче. Не расходуйте ресурсы участвующих кошельков параллельно из SafePal; нужен доверенный RPC.

## 8. Возврат, пауза, учитель и End Game

| Действие | Результат | Учителю |
|---|---|---|
| Закончен полный MIX-план | Сохранённые возвраты → CAMPAIGN_RESTORED, пауза | Ничего |
| Rebalance / вернуть доли | Отмена будущего MIX, возврат исходных ставок → пауза | Ничего |
| Защита дедлайна | Досрочный возврат → пауза; ручные одобрения всё ещё нужны | Ничего |
| End Game с паролем | Возврат, если нужен, затем ровно 1 TRX с каждого вступившего адреса; COMPLETE после подтверждений | Выплаты |

Досрочный возврат показывает число нужных переводов. При транзакции в полёте расчёт ждёт её результата. После этого доли группируются по чужому держателю и исходному владельцу: **прямые holder → owner**. Просто выровнять суммарные балансы без возврата долей недостаточно. Повторное нажатие возврата переиспользует карту/одобрения. Независимые возвраты других отправителей могут идти, пока один ждёт ресурсы. Резерв не расходуется.

Пауза переживает перезапуск. Доступны отчёты, изменение участников, новый полный план или End; автоматического возобновления/выплат нет.

**Изменить адрес учителя** проверяет адрес/активацию, сохраняет значение в БД и аудит. JSON смонтирован read-only и служит исходной конфигурацией; защищённое значение БД имеет приоритет и сохраняется при запуске с прежним JSON. Не нужно удалять БД или править SQL. Не меняйте JSON на третий неизвестный адрес после инициализации — используйте кнопку. Смена заблокирована при транзакции в полёте, неопределённом результате или незавершённом End. Старые выплаты сохраняют прежнего фактического получателя.

Только End устанавливает `payAfterReturn=true`. Он сохраняет карту возвратов и выплат, показывает её на графе, сохраняет требования Approve/Auto и ресурса. Повторный End не дублирует выплаты. Возврат не отменяет уже принятое намерение End. Общий баланс учителя не проверяется: его посторонние операции не принадлежат игре, проверяются квитанции **наших конкретных выплат**.

## 9. Sun, остановка сервера и восстановление

При вступлении резерв — `баланс − 1 000 000 Sun`. Только ставка участвует в плане. Дополнительное поступление после сверки сохраняется на адресе, куда пришло; не покрывает недостачу другого участника и не увеличивает выплату. После End на кошельках остаётся резерв.

Подпись и txID записываются **до broadcast**. После сбоя проверяется тот же txID; допустимая повторная передача использует ту же подпись, а не новый перевод. Успешная нулевая комиссия проверяется по подтверждённой квитанции. CONFIRMED и перемещение долей фиксируются одной DB-транзакцией; повторная квитанция не перемещает их второй раз.

В БД сохраняются все альтернативные варианты, выбранный вариант, блокировка настройки, режим расписания, время готовности ресурса, следующий запрос, случайный интервал и весь исполняемый план, профиль/seed, одобрения, фаза, закрывающая карта, намерение End и позиции долей. Перезапуск посреди MIX/возврата/End продолжает сохранённую фазу после проверки транзакции в полёте. После восстановления остаётся пауза; HALTED также остаётся остановленным.

Перед отправками позиции сверяются с независимым воспроизведением журнала и балансами участников плюс резервы. Недостача 1 Sun, комиссия, противоречивые доли или неопределённый результат блокируют дальнейшие отправки. RPC-ошибка не считается доказательством потери денег и не разрешает новый перевод. **Review extra Sun & resume** обрабатывает только доказанный положительный излишек/старую проверку учителя после сверки участников; повреждение учёта ею не обходится.

**Одна база — один API-воркер.** Не запускайте второй экземпляр с теми же ключами. Не удаляйте БД и не заменяйте адреса слотов. При потере данных сначала восстановите историю и сверьте сеть; нельзя заново принять промежуточные балансы за исходные ставки.

## 10. Telegram

В `.env.example`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID`, `TELEGRAM_PINNED_MESSAGE_ID`, необязательный `TELEGRAM_DASHBOARD_URL`.

1. Получите токен у `@BotFather`, добавьте бота администратором канала с правом публикации/редактирования.
2. Создайте **текстовый пост от бота**, закрепите, запишите message ID. Чужое сообщение может быть недоступно для редактирования.
3. Укажите ID канала (`-100…`) или `@username`, ID поста и доступную участникам HTTPS-ссылку. Localhost остальных участников не ведёт на ваш сервер.
4. После изменения `.env`: `docker compose up -d --force-recreate api`. Обычный restart не подставляет новые переменные.

Пост содержит ближайшие шаги очереди, сумму/тип/время MSK/статус и последние три символа адресов; большой список сокращается до лимита Telegram. Отдельные уведомления показывают события/подтверждения и фактический Bandwidth, если он известен. Сотни будущих строк дают одно событие планирования. Telegram переводы не одобряет.

Проверка переменных без печати токена:

```bash
docker compose exec -T api node -e 'console.log({token:!!process.env.TELEGRAM_BOT_TOKEN,channel:!!process.env.TELEGRAM_CHANNEL_ID,pin:!!process.env.TELEGRAM_PINNED_MESSAGE_ID})'
docker compose logs --tail=120 api
```

Доставка/повторы хранятся в БД; ошибки Telegram не останавливают игру. При сбое между успешной отправкой и записью результата возможен дубль уведомления. Оставьте три обязательных поля пустыми для отключения.

Тесты API и клиента используют изолированные mock-базы/поддельные HTTP/Telegram-ответы, не Mainnet. Проверяются конкурентные транзакции и чтение отчётов для 17 участников, очередь записей и rollback, атомарность Telegram-курсора, медленный опрос/частичные ошибки клиента, личная предыстория FIFO, точные дробные Sun, связь peer → peer с положительной долей, пакеты нескольких владельцев, исключение чужих/неподтверждённых/поздних строк, граница архивной кампании, кеш и его обновление, частичные старые журналы, неизвестный Bandwidth, независимые опции схемы/CSV, отсутствие записей при чтении отчёта, включение ускорения посреди исполнения, сохранение схемы/одобрений, блокировка готовых поздних отправителей, порог 407 и более высокий размерный порог, перезапуск во время случайной паузы, отказ RPC, а также: сохранение каждого Sun, разные профили/размеры группы, полные планы, справедливый MIX-бюджет, одобрения, прогноз ресурса, резерв/дефицит, повторная квитанция, выключение сервера, возврат/пауза, учитель, экспорт и отсутствие повторных выплат.

Публичные GET:

- `/api/state`, `/api/graph`, `/api/queue`, `/api/health`;
- `/api/logs/:address`, `/api/history/:address?status=CONFIRMED&before=<sequence>` — физическая история, до 50 строк страницы;
- `/api/campaign`, `/api/campaigns`, `/api/campaign/return/preview`;
- `/api/plans` — сохранённые варианты, показатели и доступность настройки;
- `/api/plans/:id/report/:address?format=csv` — JSON-отчёт без format или CSV конкретного варианта; необязательно `includePrehistory=1`;
- `/api/campaign/report/:address?campaignId=<id>` — движение исходной ставки; необязательно `includePrehistory=1` для предыстории;
- тот же report с `&format=csv` — экспорт; `includePrehistory=1` включает старые строки, `0` или отсутствие параметра исключает их;
- `/api/rebalance/preview`, `/api/recovery/preview` — старый расчёт/восстановление, без подписания.

POST с JSON-полем `password`:

- `/api/admin/plans/generate` — необязательно `totalDays`, `deadlineAt` (ISO с часовым поясом), создаёт только вариант;
- `/api/admin/plans/current` — сохранить ещё не исполнявшийся текущий план и перейти к подготовке;
- `/api/admin/plans/:id/select` — выбрать сохранённый вариант;
- `/api/admin/plans/:id/swap` — `first`, `second` (полные адреса двух участников);
- `/api/admin/start` — запуск выбранного варианта; для совместимости без варианта может создать и запустить план с `totalDays`, `deadlineAt`; при выбранном варианте его параметры имеют приоритет;
- `/api/admin/campaign/accelerate` — включить ускоренный MIX без изменения схемы или одобрений; допустимо после начала подписания;
- `/api/admin/teacher` — `address`;
- `/api/admin/campaign/return`, `/api/admin/rebalance` — возврат и пауза;
- `/api/admin/end` — единственное разрешение выплат учителю;
- `/api/admin/queue/:id/approve`;
- `/api/admin/wallets/:address/mix-enabled`, `/autoapprove` — `enabled: true/false`;
- `/api/admin/resume` — после успешной проверки причины остановки.

Старый `/mix-amounts` возвращает 410, `/replan` не меняет кампанию. Команды ограничены по частоте; публичные ответы не содержат ключей и подписанных payload.
