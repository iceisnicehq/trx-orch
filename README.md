# TRX Pool Observatory — 17 слотов, динамический состав игры

Приложение по умолчанию работает с **TRON Mainnet**. В `config/wallets.json` всегда остаются **17 адресов и приватных ключей**, но в игру можно включить только готовые кошельки. Для Start нужны **минимум два** выбранных и уже активированных адреса с балансом **не меньше 1 TRX** каждый. Остальные адреса пока не участвуют; их можно добавить позднее отдельной галочкой **Mix**.

Каждый участник вносит в расчёт **ровно 1 000 000 Sun (1 TRX)**. Например, если у него 1.000011 TRX, его 11 Sun запоминаются как личный остаток. Если позже на уже вступивший кошелёк придут дополнительные Sun, приложение сверит его баланс с подтверждённой историей и добавит только доказанный положительный излишек к личному резерву. Планирование и отправка игровых переводов этот резерв не расходуют. В конце баланс каждого вступившего кошелька сначала приводится к `1 TRX + его личный резерв`, затем он переводит учителю **ровно 1 TRX**; резерв остаётся на прежнем адресе. Поэтому сумма по всем 17 адресам, например 15.000011 TRX, не мешает стартовать с двумя выбранными и профинансированными участниками.

**Rebalance** возвращает каждому уже вступившему кошельку `1 TRX + его исходный остаток`, показывает число внутренних переводов и затем автоматически продолжает игру. **End game** выполняет такой расчёт и дополнительно отправляет по 1 TRX учителю. Режим **LIST** позволяет гонять суммы ровно 1 или 0,5 TRX по цепочке; **RANDOM** сохраняет прежние небольшие случайные суммы. Режим и список хранятся в базе между перезапусками.

## 1. Подготовьте Mainnet и ключи

1. Создайте ключ в [консоли TronGrid](https://www.trongrid.io/) и запишите его в `.env`. `TRON_PRO_API_KEY` — ключ доступа к RPC с лимитами запросов; **это не приватный ключ кошелька**. [Инструкция TRON](https://developers.tron.network/reference/select-network).
2. Скопируйте `.env.example` в `.env`. Оставьте `TRON_MODE=live`, `TRON_FULL_HOST=https://api.trongrid.io`, `WEB_BIND_HOST=127.0.0.1`; заполните `TRON_PRO_API_KEY` и задайте собственный `ADMIN_PASSWORD`. Если пароль не задан, действует исходный публично известный `P@ssw0rd12344321` — не оставляйте его для кошельков с деньгами.
3. В `config/wallets.json` заполните адрес учителя и **все 17 слотов**: `slot` от 1 до 17, адрес TRON и соответствующий приватный ключ в 64 шестнадцатеричных символа. Пока не готовый участник всё равно присутствует в конфигурации, но его галочка **Mix** остаётся выключенной. Адрес учителя — только получатель; его приватный ключ не нужен.
4. Проверьте, что учитель и выбранные участники уже **активированы в Mainnet**. Перевод на неактивированный адрес может списать плату за создание аккаунта; приложение не включает такие адреса в игру. [Документация TRON об активации](https://developers.tron.network/docs/account).

Файл кошельков выглядит так (настоящий файл уже содержит 17 пустых слотов):

```json
{
  "teacherAddress": "T...",
  "wallets": [
    { "slot": 1, "address": "T...", "privateKey": "64-символьный hex-ключ" },
    { "slot": 2, "address": "T...", "privateKey": "64-символьный hex-ключ" }
  ]
}
```

Это **серверное подписание**: внесение ключа в JSON даёт серверу возможность подписывать транзакции от имени кошелька. Одобрение в очереди происходит на сервере, **не в приложении SafePal**. Приватные ключи аппаратных SafePal S1/X1 должны оставаться на устройстве: эта версия не подписывает через аппаратный кошелёк. Никому не отправляйте мнемоники и ключи в переписке. Храните `.env`, `config/wallets.json`, базу и резервные копии с ограниченным доступом.

## 2. Запустите

Из каталога проекта:

```bash
cp .env.example .env
# Заполните .env и config/wallets.json до запуска.
docker compose up -d --build
docker compose logs -f api web
```

Команда использует **`docker compose` с пробелом**. Старый Python `docker-compose` может завершиться ошибкой `Not supported URL scheme http+docker`. Если в Ubuntu 22.04 `apt` не находит `docker-compose-plugin` (репозиторий Docker не подключён), для пользователя `root` с архитектурой `x86_64` можно поставить [официальный CLI-плагин вручную](https://docs.docker.com/compose/install/linux/):

```bash
uname -m
apt-get install -y curl
mkdir -p /root/.docker/cli-plugins
curl -fSL https://github.com/docker/compose/releases/download/v5.5.0/docker-compose-linux-x86_64 -o /root/.docker/cli-plugins/docker-compose
chmod +x /root/.docker/cli-plugins/docker-compose
docker compose version
```

Веб-интерфейс слушает только `127.0.0.1:8080` на сервере. На своём компьютере откройте туннель `ssh -L 8080:127.0.0.1:8080 root@IP_СЕРВЕРА`, затем перейдите на `http://localhost:8080`. Веб-образ задаёт Nginx правильный корень `/usr/share/nginx/html`; образ API устанавливает OpenSSL для Prisma.

Если сборка `web` завершилась ошибкой `host not found in upstream "api"` на строке `RUN ... && nginx -t`, обновите `web/Dockerfile` из этого архива. Проверка наличия `index.html` выполняется при сборке, а адрес `api` разрешается при запуске контейнеров в сети Compose. Для быстрого исправления в уже установленном проекте выполните:

```bash
cd ~/trx_blockchain_seminar/trx-orchestrator
python3 - <<'PY'
from pathlib import Path
p = Path('web/Dockerfile')
old = 'RUN test -s /usr/share/nginx/html/index.html && nginx -t'
content = p.read_text()
if old not in content:
    raise SystemExit('Строка не найдена: проверьте web/Dockerfile вручную')
p.write_text(content.replace(old, 'RUN test -s /usr/share/nginx/html/index.html', 1))
PY
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 api web
```

Предупреждение о `buildx` и сообщение Vite про размер JS-файла не являются причиной этой ошибки. Если после успешной сборки API остаётся в состоянии `Exited (137)`, изучите его новые логи: код 137 означает принудительное завершение процесса, но сам по себе не объясняет причину. Не удаляйте volume базы ради исправления сборки.

Если галочка **Mix** кратко меняется обратно во время обновления экрана, дождитесь следующего обновления и проверьте состояние кошелька в `GET /api/state` или событие `PARTICIPANT_SELECTION` в публичном аудите. В обновлённом интерфейсе запоздавший ответ старого запроса больше не перезаписывает свежий выбор; ошибка сохранения показывается прямо в окне пароля. Запись `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR` в старых логах API означает несогласованную настройку Nginx и Express для определения IP; новая версия доверяет ровно одному прокси и очищает остальные передаваемые заголовки. Запись `Tick: Engine is busy; retry shortly` означала, что фоновый таймер застал обработчик занятым: новая версия пропускает такой повторный тик. Для этих изменений обновите **оба образа** командой `docker compose up -d --build`. [Настройка Express за прокси](https://expressjs.com/en/guide/behind-proxies/).

## 3. Выберите участников и одобряйте вручную

1. В блоке **Mix / autoapprove** отметьте галочкой **Mix** любые два или больше кошелька с балансом от 1 TRX. Каждая галочка требует пароль. Если у адреса недостаточно средств или он не активирован, сервер отклонит включение, не прерывая игру.
2. Нажмите **Start** с паролем. Система фиксирует для выбранных адресов ставку 1 TRX и исходный остаток Sun, создаёт скользящую очередь ближайших переводов в пределах суток и ждёт одобрения. В RANDOM в очереди **не больше одного незавершённого исходящего MIX на кошелёк**; в LIST — **только один незавершённый MIX на всю игру**. Start сам по себе не разрешает переводы, если **Auto** выключен.
3. В очереди проверьте адреса, сумму и время; нажимайте **Approve** и вводите пароль. Переводы выполняются по порядку, после запланированного времени, подтверждения предыдущей транзакции и свежей проверки бесплатного Bandwidth.
4. Когда следующий участник получит 1 TRX, включите его **Mix**. Система отменит ещё не отправленные маршруты MIX (в том числе ранее одобренные), дождётся подтверждения уже отправленной транзакции, добавит адрес с его реальным балансом и построит новый план. Новые строки очереди снова требуют ручного одобрения. Если после выбора баланс адреса успеет упасть ниже 1 TRX, включение будет отклонено и это появится в журнале.
5. Снятие галочки **Mix** у уже вступившего участника исключает его из **будущего микса**, но он остаётся частью учтённого пула и финального расчёта. Если разрешённых для микса кошельков стало меньше двух, новые планы приостанавливаются до включения второго.
6. После периода наблюдения можно отдельно включить **Auto** у каждого выбранного кошелька, также с паролем. Auto автоматически одобряет его существующие и будущие исходящие строки. Выключение Auto не отменяет уже выданные одобрения. Управление Mix и Auto независимое.
7. В режиме **RANDOM** строки очереди получают случайный базовый интервал **от 1 до 2 часов**; при нехватке Bandwidth они назначаются позже. **Только после подтверждения** перевода сервер узнаёт его фактический расход и время блока, поэтому лишь тогда создаёт следующую исходящую строку этого отправителя. Уже одобренные строки других кошельков сохраняются. Нажмите **Replan** с паролем, если хотите отменить все ещё не отправленные MIX и заново построить ближайшую очередь; это также отменит их прежние одобрения. Выполненные переводы остаются в аудите. В RANDOM движок не отправит очередной MIX раньше чем через час после подтверждения предыдущего; задержки одобрения, блока или Bandwidth могут увеличить реальный интервал свыше двух часов. В LIST отдельного часового интервала нет — действуют одобрение, подтверждение предыдущего шага и проверки ресурса.

### Настройка сумм: RANDOM и LIST

В блоке **MIX AMOUNTS** выберите **RANDOM** для прежних случайных дробных сумм либо **LIST**, запишите на каждой строке `1` или `0.5` (TRX), затем нажмите **Save transfer settings** и введите пароль. Список из 1–64 строк повторяется по кругу: например, `1`, затем `0.5`, затем опять `1`. Другие суммы сервер не принимает. По умолчанию действует RANDOM; заполнение поля без сохранения ничего не меняет.

В LIST планируется **ровно один следующий перевод**. После его подтверждения сервер узнаёт фактические балансы и расход Bandwidth, сдвигает указатель списка и запрашивает свежий ресурс всех включённых кошельков. Для следующей суммы он рассматривает только **вступивших в игру, включённых для Mix** отправителей с достаточной игровой суммой. Если хотя бы один из них уже имеет **400 или больше свободных бесплатных пунктов**, первым выбирается кошелёк с **максимальным** остатком Bandwidth; при равенстве преимущество имеет получатель предыдущего подтверждённого MIX, затем выбор случайный. Это позволяет использовать новый кошелёк с 600 пунктами раньше кошелька с 342 пунктами. Если все подходящие отправители ниже 400, выбирается тот, у кого прогноз восстановления до 400 **с часовым запасом** наступает раньше. Кошельки, помеченные **Outside game**, в выборах не участвуют, даже если у них 600 пунктов; сначала включите нужный кошелёк через Mix.

Получатель выбирается из остальных включённых кошельков: сначала среди тех, кто **после получения** будет иметь сумму для следующей строки LIST, затем с приоритетом большего доступного Bandwidth и случайным выбором при равенстве. Это помогает продолжить цепочку без лишнего ожидания, но не гарантирует передачу строго от каждого получателя следующему: готовность ресурсов важнее. Если подходящий отправитель уже имеет 400 пунктов, запись LIST назначается **сейчас**, без искусственного ожидания 1–2 часов; перевод всё равно требует одобрения или Auto и повторной проверки Bandwidth перед подписанием/отправкой. Если по прогнозу ни один отправитель не достигнет порога в ближайшие 24 часа, новый шаг пока не создаётся: планировщик проверит позже. Перевод 1 TRX из кошелька с ровно 1 TRX игровой доли оставляет его игровую долю равной нулю; при большем балансе сумма 1 или 0,5 TRX может **не равняться всему балансу адреса**. Исходные дополнительные Sun не расходуются. Если у включённых адресов не хватает игровой суммы для следующей строки, можно включить другой кошелёк, изменить список либо нажать Rebalance.

Сохранение нового режима/списка сбрасывает указатель на первую строку и отменяет все ещё не отправленные MIX и их одобрения; подтверждённые операции остаются. Если уже есть отправленный перевод без чека, сначала дождитесь подтверждения, затем сохраните настройку. Подтверждения для следующих шагов LIST нужны вручную, если у отправителя не включён Auto. Защитный порог 400 действует в обоих режимах; **часовой запас применяется тогда, когда приходится прогнозировать восстановление**. Уже стоящая в очереди одобренная LIST-строка **не меняет отправителя сама собой** после обновления приложения: это сохранило бы старое одобрение для нового маршрута. Чтобы применить новый выбор сразу, нажмите **Replan** с паролем и затем заново одобрите созданную строку; если оставите прежнюю, новая логика начнёт действовать после её подтверждения.

### Необязательный журнал в Telegram

Telegram **не управляет переводами и не одобряет их**: это только отображение очереди и копия новых записей аудита. Без настройки Telegram игра работает как прежде. Для включения:

1. Создайте бота через **@BotFather** и получите **API token**. Нужен именно токен, а не числовой ID бота. Никогда не публикуйте токен и не добавляйте его в `config/wallets.json`.
2. Добавьте бота администратором в канал с правами **Post messages** и **Edit messages**. Второе право нужно, чтобы менять созданное вами сообщение. Создайте в канале обычное **текстовое** сообщение для очереди и закрепите его. Получите его `message_id`, например последнюю числовую часть ссылки на пост. Если сообщение удалено или у бота нет прав на редактирование, в логах API появится ошибка Telegram; переводы продолжат работать.
3. Заполните `.env` и заново создайте контейнер API командой `docker compose up -d --build api`:

```dotenv
TELEGRAM_BOT_TOKEN=123456:your_secret_from_BotFather
TELEGRAM_CHANNEL_ID=-1001234567890
TELEGRAM_PINNED_MESSAGE_ID=123
# Необязательно: HTTPS-адрес интерфейса, доступный участникам канала.
TELEGRAM_DASHBOARD_URL=
```

Для публичного канала вместо числового `TELEGRAM_CHANNEL_ID` можно использовать `@channelname`. Включение требует **все три** обязательных значения; если они пустые, интеграция выключена. `TELEGRAM_DASHBOARD_URL` оставьте пустым при доступе к веб-интерфейсу только через локальный SSH-туннель: `localhost` у другого участника откроет его собственный компьютер.

Закреплённое сообщение изменяется при изменении очереди и показывает её **фактические** открытые строки: номер, тип, `Node N (последние 3 символа адреса)`, направление, сумму, время по Москве и статус. Сообщение ограничено 4096 символами: если очередь длиннее, видимая часть завершается счётчиком скрытых строк. После каждого нового события аудита бот отправляет отдельный пост; для переводов в нём указаны адреса в сокращённом виде, сумма и дата/время, а для подтверждения — фактический `receipt.net_usage` **только если узел его сообщил**, плюс `txID`. Системные события тоже публикуются; `FATAL` отправляется перед обычной накопившейся очередью уведомлений. Текущая очередь и полная история всегда остаются в веб-интерфейсе.

Бот начинает с **новых** записей аудита после включения, не засыпая канал старой историей; уже стоящий в очереди перевод попадёт в Telegram, если его подтверждение произойдёт позже. Курсор аудита и неотправленные сообщения сохраняются в том же SQLite volume. После перезапуска отправка продолжается, ошибки Telegram и ограничения частоты запросов повторяются с задержкой и **не останавливают игру**. Редкий сбой ровно между успешной публикацией в Telegram и записью её результата в базу может привести к повторному посту; одинаковый `txID` поможет его узнать. При `TRON_MODE=mock` настроенный бот будет публиковать учебные события в указанный канал — для тестов оставьте три поля пустыми или используйте отдельный канал.

### Как планируется бесплатный Bandwidth

У активированного адреса сейчас обычно **600 бесплатных пунктов Bandwidth**. Они восстанавливаются **постепенно за скользящие 24 часа**; суточного сброса в конкретный час нет. Восстанавливается то, что было потрачено, считая от времени включения перевода в блок. Например, 28 сентября 2026 года в 22:31:39 UTC перевод потратил **267** пунктов: скорость восстановления около `267 / 24 = 11,125 пункта/час`. Если при свежей проверке доступно **346**, до защитного порога **400** не хватает 54: `54 / 11,125 ≈ 4 часа 51 минута`. С сохранённым **часом запаса** ориентировочное время следующего перевода — около **05:32–05:33 UTC 29 сентября (08:32–08:33 по Москве)**. Округление Bandwidth до целых пунктов может сдвинуть прогноз примерно на минуту. [Официальное описание восстановления](https://developers.tron.network/docs/bandwidth-and-energy).

Планировщик использует свежий ресурс отправителя, фактический расход `receipt.net_usage` и **время блока** `blockTimeStamp` только **уже подтверждённых** транзакций. Для старых подтверждённых записей с сохранённым `txID` приложение запрашивает чек при следующем планировании или ожидании и сохраняет недостающие данные без изменения времени записи в аудите. Если часть использования неизвестна, прогноз считает её восстановление осторожно от момента свежего снимка ресурса. Если было несколько переводов, TRON объединяет состояние окна восстановления и прогноз остаётся приблизительным. Расход ещё не выполненного перевода **не угадывается**, потому что второй исходящий перевод того же кошелька появится в очереди только после подтверждения первого.

В RANDOM сохраняется случайный интервал 1–2 часа. В LIST, если уже есть отправитель с 400+ пунктами, шаг готов к одобрению **сейчас**; время в веб-очереди обозначается **Due now**. Если отправителю нужно восстановление Bandwidth, строка назначается не раньше расчётного достижения 400 **плюс час**. Это время видно в столбце **Schedule**; общее сообщение `Bandwidth forecast...` больше не добавляется. Одобренная вручную строка остаётся одобренной. Если при наступлении назначенного времени реальный остаток меньше 400, система снова переносит её по свежим данным узла; подтверждение администратора заново не требуется. Пока время ещё не наступило, приложение не опрашивает Bandwidth отправителя каждую минуту ради этого перевода; проверки балансов игрового пула продолжаются для контроля сохранности средств.

При отправке сервер запрашивает `trx.getBandwidth` и бесплатный остаток через `getAccountResources` **до построения**, затем рассчитывает размер **подписанной** нативной транзакции по формуле TRON с дополнительными 16 пунктами запаса и проверяет доступность снова. Непосредственно **перед отправкой** ресурс проверяется ещё раз. Требуется не меньше **400 пунктов и расчётного размера транзакции**, если тот больше 400. Одобрение **не отправит** перевод при недостатке ресурса. После подтверждения фактический `receipt.net_usage`, время блока и нулевая комиссия сохраняются в публичном аудите; если старый чек недоступен, расход остаётся неизвестным. При изменении ресурса между проверкой и включением в блок абсолютной математической гарантии нулевых затрат нет, поэтому выявленная ненулевая комиссия останавливает игру. [Формула размера](https://developers.tron.network/docs/faq), [чек транзакции](https://developers.tron.network/reference/gettransactioninfobyid).

Если уже вступивший адрес получит дополнительные Sun, проверка перед следующим игровым действием сравнит **каждый** баланс с исходным остатком и всеми подтверждёнными переводами. Положительная разница становится личным резервом этого адреса и записывается в аудит как `EXTRA_RESERVE`; она не добавляется к 1 TRX ставки и не уйдёт учителю. Например, кошелёк вступил с 1.000001 TRX и позже получил ещё 1 Sun: защищённый резерв станет 2 Sun. Отрицательная разница, ненулевая комиссия, расходящиеся данные об учителе или неопределённый перевод всё ещё останавливают игру. Старайтесь не совершать внешних переводов с игровых адресов: приложение не может определить происхождение дополнительного входящего Sun, только подтвердить его наличие и сохранность исходной игровой доли. Пополнять будущих участников удобнее до включения Mix.

Показатель **Game stake** исключает личные дополнительные Sun и кошельки вне игры. Сумма **Across all 17 slots** — только обзор всех адресов, а не требуемый размер игрового пула. Граф показывает все 17 слотов, выделяет разрешённых для микса и отдельно отображает подтверждённые и запланированные маршруты.

Граф открывается в режиме **Upcoming**, чтобы будущие MIX не перекрывались с историей. Переключатели **Executed / Settlement / All** показывают остальные части карты; при Rebalance или End включается Settlement и отображается **текущая** карта расчёта. Когда Rebalance завершится, интерфейс вернётся к Upcoming. Повторяющиеся переводы в одном направлении объединены в линию: под графом показаны и **сумма TRX**, и **количество операций** (`1 tx` значит одна транзакция, а не 1 TRX). Сводка также показывает суммарную сумму видимых переводов, а подробности выбранного маршрута — отдельные суммы, статусы и время. Ниже расположена небольшая лента шести последних подтверждённых переводов по номеру транзакции, от старых к новым: стрелки показывают ход времени вперёд, а лента помогает видеть последовательность, но соседние карточки могут относиться к разным маршрутам. Числа внутри кругов — номера кошельков, `T` — адрес учителя; активные кошельки расположены отдельно от не участвующих. Узлы можно перетаскивать, и их позиции сохраняются в браузере между обновлениями страницы. Кнопка **Reset layout** возвращает исходное расположение.

**История отдельного узла:** нажмите на круг кошелька на графе или кнопку **History** рядом с ним в списке WALLETS. По умолчанию переключатель **Confirmed** показывает только подтверждённые входящие и исходящие MIX, REBALANCE и PAYOUT; рядом видна компактная цепочка нескольких последних подтверждений. **All** дополнительно показывает ожидающие одобрения, отправленные и отменённые планы. В карточках есть сумма, адреса, время MSK, статус, фактический Bandwidth и `txID`, если они есть. Фильтрация и подсчёт выполняются на сервере по **всей истории**, а не только по первой странице: **Load older** загружает следующие 50 записей выбранного фильтра без ограничения на глубину, **Refresh** загружает новейшие. В блоке **PUBLIC AUDIT** есть такие же кнопки для списка переводов; системные события аудита видны отдельно при обоих фильтрах. Щелчок по узлу также сохраняет фильтр по адресу в PUBLIC AUDIT. Адрес учителя можно открыть таким же образом на графе.

## 4. Rebalance, End game и восстановление после выключения

**Rebalance** доступен во время MIXING. Перед запросом пароля он показывает **точное минимальное количество** внутренних переводов для текущих подтверждённых балансов и сам маршрут. Это снимок на момент запроса: если перевод уже отправлен и ещё не подтверждён, вместо количества будет сообщение об ожидании чека; карта и её число шагов появятся после него. Если после просмотра другой перевод успеет подтвердиться до нажатия Confirm, сохранённая карта рассчитывается заново по свежим балансам. Rebalance отменяет ещё не отправленные MIX и их одобрения, ждёт транзакцию в полёте, если она есть, и сохраняет расчёт в БД. Он включает **все вступившие** кошельки, даже если у них снята галочка Mix, возвращая каждому 1 TRX и весь его защищённый личный резерв. Перевода учителю здесь **нет**. На экране видны карта, открытые строки REBALANCE и счётчик подтверждённых шагов. Как и при End, каждый шаг требует **Approve** с паролем, если у отправителя не включён Auto. После последнего подтверждения приложение сверяет каждый баланс, возвращается к MIXING и создаёт новую очередь; LIST снова начинается с первой строки.

**End game** останавливает микс, дожидается любой транзакции в полёте и **атомарно** сохраняет всю карту расчёта и фазу `SETTLING`. Сначала внутренние переводы возвращают каждому вступившему участнику его 1 TRX и весь защищённый личный резерв; затем каждый из этих участников переводит учителю **ровно 1 TRX**. Адреса, так и не вступившие в игру, не участвуют в выплате. Все шаги видны в графе сразу после создания карты. Переводы End также требуют ручного Approve либо включённого Auto соответствующего отправителя.

Если вы всё-таки нажали **End game** во время Rebalance, ещё не отправленные шаги REBALANCE отменяются, а новая карта End рассчитывается из подтверждённого состояния после возможного перевода в полёте. Следите за очередью и давайте одобрение уже новым шагам: старые отменённые одобрения не переносятся.

База SQLite находится в постоянном Docker volume `db-data` и работает в WAL-режиме. При обычном `docker compose stop`, перезапуске VM, обновлении образов или `docker compose up -d --build` сохраняются выбор, подтверждения, очередь и фаза. Стартовый скрипт не создаёт пустую базу поверх исчезнувшего файла и проверяет целостность SQLite перед работой. На запуске API:

- В `MIXING` продолжает существующую очередь и пополняет её после подтверждения переводов. В RANDOM действует одна открытая строка на отправителя; в LIST — одна открытая строка на всю игру, следующая сумма и получатель вычисляются только после подтверждения. При обновлении старого образа сохраняет **самую раннюю** незавершённую строку MIX каждого отправителя и её одобрение, отменяет более поздние дубли, записывая отмену в аудит. Подписанную транзакцию в полёте не отменяет. Ожидающие добавления адреса входят только после подтверждения предыдущего перевода.
- В `REBALANCE_REQUESTED` ждёт подтверждения перевода в полёте и создаёт карту Rebalance один раз. В `REBALANCING` продолжает сохранённые внутренние шаги с первой незавершённой строки; уже подтверждённые не отправляет повторно. После сверки балансов возобновляет MIXING. Количество шагов и выбранный режим сумм сохраняются в БД.
- В `END_REQUESTED` дожидается текущей транзакции и создаёт карту выплат один раз. Уже сохранённая карта повторно не создаётся.
- В `SETTLING` продолжает с первой незавершённой строки; выполненные выплаты не отправляются ещё раз. Одобрения сохраняются.
- Для `SUBMITTING` и `SUBMITTED` проверяет сохранённый `txID`. Если ответ на отправку пропал, может повторить **ту же самую подписанную транзакцию** до её истечения и при достаточном бесплатном Bandwidth; это тот же `txID`, а не второй перевод. Подтверждение и комиссия проверяются по блокчейну. Если исход остался неопределённым дольше 15 минут, фаза становится `HALTED` для ручной сверки, без создания новой транзакции. [TRON об отправке и повторе подписанного payload](https://developers.tron.network/reference/broadcasttransaction).

При `HALTED` **не удаляйте базу и не нажимайте Start повторно**. Если старый образ остановился только из-за *положительного* излишка, после обновления приложения появится **Review extra Sun & resume**. Нажмите кнопку: сервер заново читает балансы из сети и подтверждённые переводы, а окно показывает конкретные адреса, сколько новых Sun останется на каждом, и фазу продолжения. Проверьте список, введите пароль администратора и подтвердите. Сервер повторяет сверку, записывает `EXTRA_RESERVE` и `RESUMED`, затем продолжает сохранённую очередь с прежними одобрениями. При включённом Auto очередной MIX может отправиться сразу после восстановления, если выполнены время и все проверки Bandwidth.

Для случая `Pool invariant violated: 12000011 Sun, expected 12000010` новая проверка должна показать **ровно +1 Sun на конкретном кошельке**, если других изменений баланса не было. Выплата учителю при последующем End остаётся ровно 1 TRX с каждого вступившего кошелька. Если предпросмотр показывает другие суммы или `Resume unavailable`, сначала изучите `docker compose logs --tail=200 api`, аудит и сохранённый `txID`: восстановление доступно только для старой ошибки *положительного* пула при однозначной истории, без неопределённых отправок, недостачи или комиссий. Ошибки чека, недостачи или другого происхождения автоматически не разрешаются. Не запускайте два экземпляра API на одной SQLite базе.

Перед обновлением проекта сделайте резервную копию после остановки API:

```bash
docker compose stop api
mkdir -p ./pool-backup
docker compose cp api:/data/. ./pool-backup/
docker compose start api
```

Сохраните копию `pool-backup` вместе с соответствующими `.env` и `config/wallets.json` в закрытом месте. В WAL-режиме файлы `pool.db-wal` и `pool.db-shm`, если они есть, относятся к той же базе. **Не применяйте `docker compose down -v` и не заменяйте volume новой пустой БД** при обновлении.

Если новый `trx-orchestrator-source.zip` уже скопирован в `~/trx_blockchain_seminar/` рядом с текущим проектом, замените только код и документацию:

```bash
cd ~/trx_blockchain_seminar
mkdir -p upgrade-staging
unzip -o -q trx-orchestrator-source.zip -d upgrade-staging
cd trx-orchestrator
docker compose stop api
mkdir -p ./pool-backup
docker compose cp api:/data/. ./pool-backup/
cp -a ../upgrade-staging/trx-orchestrator/api/src/. api/src/

cp -a ../upgrade-staging/trx-orchestrator/web/src/. web/src/
cp docker-compose.yml ./pool-backup/docker-compose.yml

```

Эти команды не заменяют ваши `.env`, `config/wallets.json` и volume `db-data`. Миграция `20260930000000_external_extra_reserves` добавляет только поле для сохранения фазы перед остановкой и применяется автоматически при запуске API. Если вы вручную меняли `docker-compose.yml`, сравните сохранённый файл из `pool-backup` с новым, чтобы сохранить ваши настройки и переменные `TELEGRAM_*` в окружении `api`. Уже запущенная игра сохраняет участников, текущий LIST/случайный режим, открытые переводы и их одобрения. **Существующая одобренная строка не меняет маршрут автоматически**. Если ваша игра сейчас `HALTED` с положительным излишком, сначала используйте **Review extra Sun & resume**; Replan в HALTED недоступен. В продолжающейся игре Replan отменяет открытый MIX, включая его прежнее одобрение, поэтому нажимайте его только если нужен новый маршрут. Перед одобрением проверьте `GET /api/state` и очередь. **Не удаляйте volume базы** при обновлении.

## Ограничения

Перед построением и отправкой **каждого реального** перевода приложение проверяет `trx.getBandwidth` и доступную бесплатную часть Bandwidth; используется только нативный `TransferContract`. При нехватке ресурсов перевод ждёт, поэтому End может длиться несколько дней. **Абсолютную гарантию нулевой комиссии блокчейн не даёт**: квота может измениться между проверкой и включением транзакции. Обнаруженная комиссия, недостача любого вступившего кошелька, расхождение выплат учителю или неопределённый результат после времени восстановления переводят игру в `HALTED` и записываются в журнал. Подтверждённый положительный излишек сохраняется на исходном адресе отдельно от ставки. Адреса вне игры в сверку пула не входят. [Ресурсная модель TRON](https://developers.tron.network/docs/paying-for-resources).

Для практики без движения настоящих TRX можно **явно** установить `TRON_MODE=mock` в отдельной чистой базе. По умолчанию режим `live`; mock не нужен для ручного запуска. Нельзя переиспользовать одну БД между Mainnet/mock или разными наборами адресов.

Локальная сборка: `cd api && npm ci && npx prisma generate && npm run build && npm test`; клиент: `cd web && npm ci && npm run build`.

API: публичные `GET /api/state`, `/api/graph`, `/api/queue`, `/api/logs/:address`, `/api/history/:address?before=<sequence>`, `/api/rebalance/preview`, `/api/recovery/preview`; защищённые паролем `POST /api/admin/start`, `/replan`, `/rebalance`, `/end`, `/resume-excess`, `/mix-amounts`, `/queue/:id/approve`, `/wallets/:address/mix-enabled` и `/wallets/:address/autoapprove`. Для `/api/history/:address` и `/api/logs/:address` параметр `status=CONFIRMED` включает серверный фильтр; `status=ALL` (по умолчанию для прямого API-запроса) возвращает все статусы. `/api/history/:address` возвращает `{ address, total, items, nextBefore }` с максимум 50 записями и без приватных ключей/подписанных payload; для старых записей передайте полученное `nextBefore` как `before` с тем же `status`, пока оно не станет `null`. Для `/mix-amounts` передавайте JSON `{ "password": "...", "mode": "LIST", "amountsSun": [1000000, 500000] }` или `{ "password": "...", "mode": "RANDOM" }`. Для переключателей кошельков — `{ "password": "...", "enabled": true }`; для `/rebalance` и `/resume-excess` — `{ "password": "..." }`. Оба preview ничего не подписывают и не меняют в БД.
